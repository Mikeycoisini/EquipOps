# EquipOps 架构与数据设计

> 状态：待实施的设计稿；本文件不代表代码已按此实现。  
> 日期：2026-10-22  
> 关联文档：[01-项目需求](01-项目需求.md) · [03-阶段路线与验收](03-阶段路线与验收.md)

## 1. 设计目标与决定

采用 **Spring Boot 模块化单体 + MySQL，共享数据库／共享业务表**。一家公司对应一个租户；厂区和仓库是租户内部资源。短期以两个测试租户和单默认厂区、默认仓库验证隔离；长期可扩展到多厂区／多仓库，但不承诺共享表方案适用于所有监管或合同要求。若未来客户明确要求物理隔离，再依据实际约束评估独立 Schema／数据库。

关键决定：

1. 全局用户身份可加入多个租户；每个请求只能有一个经服务端验证的当前租户。
2. 设备、工单、备件、仓库库存、流水及审计按租户归属。厂区和仓库从第一阶段开始建模，即使每租户只有一个默认值。
3. 备件目录与仓库库存分离；不继续把 `spare_parts.stock_quantity` 作为唯一库存真相。
4. 工单与库存以数据库事务、条件更新、唯一约束和幂等键处理一致性；首版不引入分布式事务和消息队列。
5. 对现有 Flyway V1 仅做增量迁移，不修改已执行迁移；迁移前备份和演练。

## 2. 模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| Identity / Tenant | 登录身份、租户成员关系、当前租户上下文、角色和后续厂区授权 | 直接修改工单或库存 |
| Equipment | 设备档案、所属租户／厂区、可用状态 | 工单流程和备件扣减 |
| WorkOrder | 报修、派单、维修、验收、状态规则和时间线 | 自行修改仓库库存数量 |
| Inventory | 备件目录、仓库库存、领用、退回、流水、后续调拨 | 绕过工单授权做业务决策 |
| Operations | 健康检查、审计查询、备份／恢复说明、指标与告警 | 作为普通租户业务入口跨租户查询 |

模块之间通过明确的服务接口协作。Controller 仅进行协议适配和入参校验；业务权限、状态规则和事务边界在 Service／领域层；Mapper 负责持久化及条件更新。避免同时以 JPA 与 MyBatis-Plus 分别修改同一业务表；在实施前确定主要持久化技术，并清理不必要依赖。

## 3. 租户与身份模型

建议新增 `tenants`、`tenant_memberships`、`tenant_member_roles`、`sites`、`warehouses`。`users` 保持全局账号。租户成员关系记录用户在企业内是否启用及角色；第二阶段可新增厂区／仓库授权表。平台运营身份与租户成员身份分离，其跨租户操作使用独立接口、最小权限与审计。

登录／切换流程：用户以全局账号认证 → 服务端列出有效租户成员关系 → 用户选择租户 → 服务端再次核验并签发仅针对该租户的短期会话／Token → 每次请求构造可信租户上下文并确认成员关系仍有效。客户端提供的企业 ID 只是“选择意图”，不构成权限。撤权后必须拒绝后续操作；首版可通过每请求核验成员关系实现，后续如加缓存必须定义失效策略。

所有业务查询、更新、删除和新增都以当前租户为前提。通过猜测其他企业的对象 ID 访问时，不能泄漏该对象详情或存在性；对同租户但无动作权限的请求返回明确的权限错误。分页、聚合、审计、导出、定时任务、文件访问及未来缓存／事件同样要显式带租户上下文。自动 SQL 过滤可作辅助防线，但不能代替服务层校验和数据库约束。

## 4. 数据模型与现有 V1 的迁移

### 4.1 目标归属

- `equipment`、`work_orders`、`work_order_logs`、`spare_parts`、`inventory_transactions`、`work_order_parts` 均有可追溯的租户归属；设备及工单记录厂区归属。
- `warehouses` 属于某租户及厂区；`warehouse_stock` 以 `(tenant_id, warehouse_id, spare_part_id)` 唯一，保存可用数量及安全库存。备件目录仅保存编号、名称、规格等主数据。
- 领用流水记录仓库、工单、操作人、业务请求号。退回流水关联原领用，确保退回数量上限可验证。工单用料可保留按工单／备件的汇总，但不能用汇总取代有仓库归属的流水。
- 业务编号采用租户范围内复合唯一约束。关键跨表引用需同时校验 `tenant_id`；可行时用复合键／约束加强数据库防线，避免仅按全局 ID 建立跨租户关联。

### 4.2 非破坏性迁移顺序

1. 在数据库副本上检查 V1 实际状态、记录数、约束和现存重复编号；备份并验证备份可读。
2. 新增租户、成员、默认厂区与默认仓库；为旧数据分配明确的默认租户，不猜测其真实企业归属。若旧数据混有多家企业，必须先人工确认映射，不能自动归为一家。
3. 使用新版本迁移增加归属列和 `warehouse_stock`；将旧备件数量及安全库存搬入默认仓库，并核对迁移前后数量。
4. 增加新的复合唯一约束和租户查询索引；确认应用代码已切换后，才在后续迁移中处理旧的全局唯一约束和旧库存列。
5. 在测试环境演练迁移及回滚／恢复。已应用的 V1 不修改；不通过直接删库重建来“解决”迁移失败。

当前 `SparePartEntity` 直接持有库存字段，`UserEntity` 和 `RoleEntity` 为全局模型，`application.properties` 还有密码默认值。这些是需要处理的现状，不是完成证明。Entity、DTO、VO、SQL、前端 API 与迁移必须成组审查。

## 5. 核心业务与事务设计

### 5.1 工单

首版状态：`PENDING`、`IN_PROGRESS`、`AWAITING_ACCEPTANCE`、`COMPLETED`。派单不切换状态；已有负责人不可被另一个并发派单请求覆盖。验收失败回到 `IN_PROGRESS`，记录原因；完成后不允许普通修改。取消与重新打开明确不在 S1 范围内，若以后加入，必须同步更新状态矩阵、迁移和测试。

每个命令按“验证租户与厂区 → 验证成员角色及对象关系 → 验证旧状态 → 条件更新 → 写日志 → 提交事务”执行。条件更新至少限定租户、工单 ID、预期状态及相关前置字段，并检查受影响行数。状态变化和 `work_order_logs` 原子提交。创建人、操作者从认证上下文获取，不从请求 DTO 信任用户 ID。维修执行人不能验收自己的工单；可验收人是报修人或有验收权限的主管。

### 5.2 库存领用、退回与幂等

库存数量是仓库维度的值。领用必须指定同租户的工单、仓库和备件；校验正数量与允许领用的工单状态。执行条件扣减：匹配租户、仓库、备件，且余额足够。扣减、用料汇总、流水及业务请求号在同一事务内完成，任何一步失败回滚。重复请求根据租户范围内的唯一请求号返回已存在结果或明确冲突，不再次扣减。

退回引用原领用流水及其仓库；在并发情况下通过锁定或条件更新保证累计退回不超过已领用。库存增加、退回流水和用料汇总同事务完成。人为调整库存应有独立权限、原因和审计，不得伪装成普通入库或退回。

### 5.3 第二阶段仓库调拨的预留

第一阶段所有领用已经显式落到默认仓库。第二阶段再增加调拨单及状态：申请 → 源仓出库／在途 → 目标仓确认入库；取消和异常处理需在第二阶段细化。调拨限同租户；源仓与目标仓各有流水；重复确认幂等。第一阶段不提前实现调拨功能，但数据模型不依赖“全租户只有一个库存数”。

## 6. API、错误与安全边界

尽量延续现有 `/api/equipment`、`/api/work-orders` 等路径，但具体 HTTP 方法、字段和分页响应以真实前后端契约核对后决定。建议通过经验证的当前租户会话维持原业务 API 路径，不允许客户端自行传入任意 `tenant_id` 绕过校验。所有写操作的请求号、仓库 ID 和预期版本／状态应有明确契约。

错误分类：入参错误、未认证、无权限／无成员关系、资源在当前租户下不存在、状态或库存冲突、内部失败。HTTP 状态和现有 `Result` 业务码保持一致；并发冲突不包装成普通成功。错误响应不包含其他租户的对象信息、SQL 或内部密钥。业务审计与技术日志分离，日志记录关联请求号与必要对象 ID，不记录密码／完整 Token。

## 7. 测试与可运维设计

- 单元测试覆盖状态允许矩阵、角色规则、退回上限、数量与参数校验。
- 使用 Testcontainers 驱动真实 MySQL 集成测试，覆盖迁移、唯一约束、条件更新、事务回滚、并发派单、最后一件并发领用、请求重试及跨租户读写。Mock 测试不能替代数据库行为测试。
- 两个测试租户、同编号设备／备件、不同角色、撤权和猜测 ID 构成固定隔离用例。分页、详情、变更、统计、导出、后台任务各自验证租户范围。
- 第二阶段才将监控告警、隔离恢复演练和运维值守作为团队试用门槛；第一阶段至少需要健康检查、错误日志及可重复部署说明。
- 在共享数据库中，整库备份不等于可安全单独恢复一家企业。单租户恢复应先在隔离环境重建，核对完整关联数据，再按受控流程回迁；真实恢复目标需与使用团队协商。

## 8. 已知风险与待决事项

1. 现有 V1 为单企业结构，且多个 Entity 同时包含 JPA 与 MyBatis-Plus 注解；实施前需要明确 ORM 主线及实际数据库是否已有数据。
2. 现有报修 Service 尚有未完成逻辑，设备更新接口和前端契约也需核实。迁移不是替代现有业务正确性检查。
3. 共享表的隔离高度依赖正确的租户上下文、查询条件和测试；不宣称等同数据库物理隔离。
4. 第二阶段调拨审批、跨厂区协作细节，以及正式运行时的恢复目标、数据保留和运营责任仍需与真实试用团队确认。

本设计完成后应先由用户审阅，再拆成逐项实施计划；没有实现与测试证据前，所有技术能力均保持“规划中”状态。
