# 企业归属与八个基础接口

## 范围及状态


用户选择：旧数据先保留，生成待核对归属清单。本次使用当前配置连接 MySQL 返回 1045，没有执行数据库写入、迁移或数据回填。下面描述的是已编写契约，不能当作已经联调通过。

## 八个接口

| 方法和路径 | 参数/请求 | 返回 Result.data |
|---|---|---|
| GET /api/equipment/{id} | 路径设备 ID | EquipmentVO |
| GET /api/work-orders | current=1,size=10,keyword,status,priority,equipmentId,assigneeUserId | IPage<WorkOrderVO> |
| GET /api/work-orders/{id}/logs | 路径工单 ID | List<WorkOrderLogVO> |
| GET /api/spare-parts | current=1,size=10,keyword,category,enabled | IPage<SparePartVO> |
| GET /api/spare-parts/{id} | 路径备件 ID | SparePartVO |
| POST /api/spare-parts | SparePartUpsertDto | SparePartVO |
| PUT /api/spare-parts/{id} | 路径 ID + SparePartUpsertDto | SparePartVO |
| GET /api/inventory/transactions | current=1,size=10,warehouseId,sparePartId,workOrderId,transactionType,referenceType,startTime,endTime | IPage<InventoryTransactionVO> |

分页始终返回 records/total/current/size，页大小限制为1..100。时间格式示例：2026-10-25T09:00:00，按本地业务时间解释，开始/结束边界均包含。列表以时间/ID或ID稳定排序。

工单分页不逐条加载日志，timeline 返回空列表，页面要按需请求 logs；不能把空 timeline 当作工单没有历史。日志沿用现有全量时间升序列表，本次没有改成分页。

备件新增请求示例：

~~~json
{"partCode":"SP-001","name":"主轴轴承","spec":"6205","minStockQuantity":2,"unit":"件","enabled":true}
~~~

备件编号、名称必填，编号企业内唯一。目录写入只允许企业管理员；查询要求有效企业成员。新增库存为0；任何非空 stockQuantity 请求都拒绝。修改不触碰库存列；spec/category/location 可清空，minStockQuantity/unit/enabled 不传则保留。stockQuantity 暂时仍是旧表兼容字段，不代表已实现仓库库存模型，后续库存模块再按迁移拆分。

库存类型保持现有 INBOUND/OUTBOUND/ADJUSTMENT，不提前引入尚未实现的退料类型。流水查询不写库。

## 归属与现有业务的最小调整

- equipment、work_orders 增加 tenantId/siteId；spare_parts 增加 tenantId；inventory_transactions 增加 tenantId/warehouseId。
- 新设备由登录企业和启用默认厂区决定归属，覆盖请求体中的归属；负责人必须是本企业有效成员。
- 工单从已验证设备继承归属；创建人、派单操作人从登录上下文取得，原 DTO 字段保留以兼容但不信任。
- 当前阶段派单限定企业管理员；负责人要求本企业启用成员和启用账号，维修资格细分角色尚未定义。原待处理/未派单规则保留，最终更新增加企业、原状态、未派单条件防覆盖。
- 设备分页、编辑、删除、状态和维修履历增加企业范围；编辑忽略主键、归属、状态及审计字段，状态仍由原独立接口调整。
- 日志先校验父工单企业归属；不通过日志 ID 或操作者 ID 推测归属。
- 本批业务异常返回 Result 与对应 HTTP 状态；数据库约束失败不暴露 SQL。

## 数据库部署顺序

1. 停止旧版本写入，备份现有库，并核对 SHOW CREATE TABLE 与 V1/V2 是否一致；设备状态枚举等手工调整也要核对。不要直接覆盖真实库。
2. 在隔离副本先审阅并执行 V3__add_business_tenant_ownership.sql。已有 V1/V2 不修改。正常启动应用会由 Flyway 执行 V3；也可手工执行但必须同时正确维护 Flyway 历史，不能两种方式重复执行。
3. V3 允许旧归属为空并建立复合外键/索引，替换设备和备件的全局编号唯一索引为企业内唯一。不删除业务记录，不修改库存余额。
4. 部署本次代码。归属 NULL 的旧记录会暂时不可见，不代表数据丢失。新增记录由服务端设置归属。数据库连接失败时不要误报接口成功。
5. 手工运行 docs/sql/ownership_pending_review.sql 导出待核对清单。当前没有可输出的真实行清单，必须先恢复连接。
6. 归属经人工确定后，填写 ownership_backfill_template.sql 的映射。停写、在同一会话执行并核对，确认后手工 COMMIT，否则 ROLLBACK。当前没有填入任何猜测 ID。
7. 全部归属完成后审阅 ownership_finalize_not_null.sql，收紧非空；正式版本应把最终收紧固化为下一份 Flyway 迁移。过渡期不要允许绕过应用的任意 SQL 写入。

复合外键防止设备挂到其他企业厂区、工单挂到其他企业设备、流水挂到其他企业备件/仓库/工单。旧记录归属未填前，复合外键中的 NULL 会跳过检查，依赖应用的企业条件隐藏；这是一段明确的迁移过渡状态，不是多租户验收完成。

MySQL DDL 会隐式提交；若 V3 部分失败，停止并核对实际结构，不能简单重跑或擅自 Flyway repair。新应用依赖 V3 字段，不能只部署 Java 代码。需要撤回代码时先停写，恢复匹配数据库结构的版本；不要通过删列回退而丢失归属信息。
