# EquipOps Python AI 增量扩展候选计划

编写日期：2026-11-02，上海时间。

状态：用户要求先规划、后续再做。本文是建议稿，不代表新增阶段已开工，也不授权安装依赖、创建接口骨架、建表、调用收费模型或上传项目数据。第三阶段原路线仍按27号文档推进。

## 1. 是否适合

适合围绕现有设备、维修工单、维护计划和备件适配，增加一个范围有限的“设备维修知识助手”。它能把维修资料与当前企业业务数据结合，给出可追溯的查询结果和处理建议。先做辅助查询与建议，不替代现有Java业务判断。

首版建议场景：维修人员查看某设备时，询问“这类故障应该先检查什么，有哪些相关维修记录？”回答区分资料中的建议与实际查到的历史工单，展示来源；信息不足时明确说明。

暂不做预测性维护、故障概率预测或自动决策：当前未确认有足够的传感器时序数据、标注样本和可靠性评估依据。

## 2. 三种方案与推荐

| 方案 | 好处 | 代价与适用范围 |
| --- | --- | --- |
| 直接使用Java接模型与检索 | 部署较简单，沿用Java学习主线 | 不符合本次希望练习Python AI的主要意图，可作对照方案 |
| Java业务主系统 + 一个Python AI辅助进程 | 保留现有业务；能练习Python、检索和工具编排 | 多一种运行环境，需要明确身份传递、超时和失败行为；推荐作为后续首版方向 |
| 一开始引入多智能体、多个AI服务和自动业务写入 | 可演示复杂编排 | 难以定位问题，偏离适中业务范围，当前不推荐 |

推荐第二种，但尚未锁定模型供应商、向量存储、Python框架版本、部署方式、接口路径或开发日程。Java业务仍是单体；一个独立Python辅助进程不等于把业务拆成微服务。

## 3. 各技术各做什么

| 技术 | 本项目中的职责 | 何时引入 |
| --- | --- | --- |
| RAG | 从设备说明书、维修规范等已授权资料检索片段，再生成有来源的回答 | 首个AI功能 |
| LangChain | 按需要使用模型适配、文档处理、检索与工具组件 | 首版选择必要组件，不为使用框架而增加抽象 |
| Function Calling / Tool Calling | 模型提出结构化的工具名与参数；程序校验后调用查询函数 | 文档问答稳定后，接入实时业务查询 |
| LangGraph | 编排有状态、多步骤、可暂停和恢复的流程 | 确实出现“查询→分析→补充资料→生成草稿→人工审阅”的需求后 |
| MCP | 让相同工具以标准协议提供给兼容客户端复用 | 普通工具稳定，并确有第二个客户端需要时；不作为首版前置条件 |

这些技术不在同一层：RAG是方法，Function Calling是模型与程序之间的调用机制，LangChain提供组件，LangGraph负责流程，MCP负责协议。LangGraph可以独立于LangChain使用，MCP也不替代业务鉴权。

## 4. 业务与身份边界

建议调用方向为“前端→Java认证入口→Python AI”，业务数据仍由Java按当前权限读取。Python不直接连接业务MySQL，不取得共享管理员账号，不接收由模型任意生成的SQL执行请求。

跨进程身份方案必须在开发前单独设计：不能信任浏览器或模型传来的tenantId，也不能只凭Python请求头里的userId授权。候选是由Java为单次AI任务创建受控上下文，并通过短期、限定用途的服务调用凭证访问白名单查询入口；有效期、重放、撤销、企业切换和传输保护均需验证。当前并不存在这一新机制，本文不假定它已实现。

每次任务绑定发起用户、企业、会话/任务身份。任务执行与恢复时重新验证权限；切换企业后旧任务结果不得显示在新企业页面。工具执行前由程序校验参数和权限，不能因为模型选中了工具就执行。

原有Session、CSRF与每请求实时角色校验保留。AI进程不可用时，设备、工单和库存原有功能仍应可用。

## 5. 建议实施顺序

### A0：准备与范围确认

- 原则上先完成第三阶段Redis共享Session与双实例这一当前单元，再决定AI试验的开始时间，不替换原工程化路线。
- 选一种设备、少量有使用权限且可提供给所选模型的资料。先支持Markdown/TXT；PDF解析和OCR后置。
- 确认模型运行位置、调用预算、资料允许出域范围、日志保留和删除方式。不上传账号、凭据、个人信息或未经许可的企业维修资料。
- 首次开工前核对当前框架稳定版本并锁定依赖，不照抄旧版API。

交付：一个场景、资料清单、数据边界和待确认设计。没有这些前提不承诺效果。

### A1：离线文档RAG最小原型

1. 解析资料，保存来源、版本、章节/页码和片段编号。
2. 切分片段、生成向量并建立可删除重建的索引。
3. 对问题检索相关片段，生成答案并返回来源引用。
4. 未找到可靠依据时给出“不足以判断”，不编造页码、手册结论或维修步骤。
5. 记录检索耗时、模型耗时、Token/调用成本；设置超时和最大输入长度。

先采用固定的检索后生成流程，比较关键词检索与向量检索；是否需要混合检索或重排由评估结果决定。向量存储尚待选型；不默认复用Session Redis，也不先增加独立数据库集群。

交付：可运行的Python原型、带来源的问答、可重复评估结果。此阶段不接业务写入。

### A2：接入一个只读业务工具

先在源码中核对设备详情、设备维修履历等现有接口契约，再选一个工具。语义名例如“查询设备维修记录”仅为规划名称，不是已创建的Java方法或URL。

工具返回结构化、有限条数的数据；实时库存、工单状态等仍查业务系统，不能把向量库中的旧信息当当前余额。模型只负责提出调用，程序处理参数校验、身份检查、调用次数与时间预算。

交付：能明确区分“文档建议”“系统查询事实”“模型推断”的回答，以及越权、超时、空数据和错误参数测试。

### A3：LangGraph维修分析与草稿流程

仅在A1/A2有价值后推进：读取授权上下文→查询历史→检索资料→生成建议→检查依据→生成维修记录草稿→等待用户查看。

图状态只保存必要信息，checkpoint、对话、索引与缓存都按企业/用户/任务隔离。任务标识不是权限凭证。恢复任务时重新检查授权；外部副作用需要幂等，不能认为checkpoint能保证业务只执行一次。限制节点数、工具循环次数、超时与Token预算。

首版草稿不自动写库。若未来允许保存，另行确认写入规则与接口：展示确切内容，用户确认后由原Java接口重新做权限、状态、幂等和事务校验。人工确认不能代替后端校验。

### A4：按需MCP适配

将已经验证的少量只读工具封装为MCP工具，验证工具发现、参数模式、调用结果、拒绝访问和客户端断开。复用原查询能力，不另写一套绕过Java的数据库访问。

本地学习可先评估stdio；远程HTTP服务须单独设计认证、授权、凭证受众和网络暴露范围，不能把本地进程示例当作远程安全方案。

只有单一客户端时可以停在A3；不用MCP并不影响RAG或工具调用成立。

### A5：集成页面与可靠性验收


AI调用限流、连接/读取超时、有限重试、成本上限与日志脱敏逐项验证。写操作和有副作用节点不可盲目重试。SSE是否需要待页面交互确认，不预先增加WebSocket。

## 6. 验收如何证明有用

先人工整理建议不少于30条小型评测集，包含有依据问答、资料缺失、跨企业、资料提示注入、错误工具参数、工具超时和幻觉诱导。题目与期望来源由人审核，不只由同一模型给自己评分。

记录检索Recall@K、答案是否有足够依据、引用是否真实、资料不足时是否正确拒答，以及延迟和成本。K、通过阈值和硬件/模型条件在原型前确认，不能先填写一个漂亮的准确率。保留原始失败例和修正前后结果。

权限方面必须覆盖企业A/B的资料、工具、对话、checkpoint、缓存、日志和返回页面，验证请求其他企业的文档ID/任务ID无法读取；不能仅靠生成答案前过滤文本。文档中的命令均视为不可信内容，不能改变工具白名单或授权。

## 7. 与Java学习及求职表达结合

Java仍承担认证、授权、事务、并发、幂等、接口和任务管理；Python承担检索与模型编排。用一个功能串联网络超时、线程池容量、任务状态、资源关闭和监控，而不是重复写两套业务。

后续可形成证据：“实现按企业隔离、引用可追溯的维修资料助手，受控调用Java只读接口，并完成缺失资料、越权及故障评估。”只有实际做过并测过后才能这样描述，当前不能写成已完成项目成果。
