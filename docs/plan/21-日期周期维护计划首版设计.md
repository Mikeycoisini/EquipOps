# 日期周期维护与巡检：首个接口设计


## 意图与方案

为当前企业设备登记定期维护或巡检任务，明确负责人、执行内容和首次到期日，后续再逐项增加查询及执行记录。

比较：日期周期易维护且可用现有设备ID；运行小时触发需要可靠运行时长更新；混合触发还需优先级和去重规则。用户已选择日期周期，首版不实现后两者。

## 第一个接口

POST /api/maintenance-plans

拟请求字段：name（必填，最多160字符）、equipmentId（必填正数）、planType（MAINTENANCE维护/INSPECTION巡检）、content（必填，最多2000字符）、cycleDays（1～3650整数）、nextDueDate（首次到期日期，YYYY-MM-DD）、assigneeUserId（必填正数）。

企业ID、厂区ID、创建人、启用状态和主键不由请求指定；企业和创建人取登录上下文，厂区继承已校验设备，启用默认true。返回MaintenancePlanVO，包括设备编号/名称、负责人显示名和上述业务字段及时间。

## 建议权限与流程

1. 仅当前企业管理员创建。
2. 校验请求，首次到期日不早于当前业务日期（Asia/Shanghai）。
3. 设备必须属于当前企业，设备所属厂区必须启用；不擅自限制设备必须RUNNING，停机设备也可能需要维护。
4. 负责人必须是当前企业启用成员且全局账号启用；不等于要求负责人必须有管理员或验收角色。
5. 插入维护计划，厂区及创建人由后端填充，事务内回查完整VO后返回。

此接口只登记计划，不生成执行记录、不新增定时任务、不自动建维修工单、不修改设备状态或库存。执行完成后的下次到期日推算、补做、逾期与重复生成规则留到执行记录接口单独确定。

## 数据与兼容性

建议新增maintenance_plans表，字段为id、tenant_id、site_id、equipment_id、name、plan_type、content、cycle_days、next_due_date、assignee_user_id、enabled、created_by、created_at、updated_at。


结构通过新增V8迁移准备，不修改V1～V7；迁移执行前单独核对目标库和备份，不因创建骨架就启动应用自动执行。计划不直接覆盖equipment.next_maintenance_at，避免与用户既有档案字段互相覆盖；之后如需汇总展示再约定口径。

## 验证目标

参数及枚举错误400、普通成员403、其他企业设备/负责人不可用、停用成员拒绝、成功查询返回本企业计划。数据库结构及真实写入需另行验证；不以空骨架编译通过宣称接口完成。
