# A8 平台可用性告警

应用恢复后由固定调度读取本机探针 SQLite 的有序事件。信任边界为操作系统保护的状态目录，应用只有读取权。通过显式配置固定端口、文件和责任账号。既有探针库首次启动新版探针后写入数据流 UUID。MySQL 按 UUID 和事件游标顺序处理，文件换代或序列断档停止续扫。证据仅含固定状态、时间和种类。单个部署配置一个探针目标。

V23 建平台告警、证据游标和人工动作表，不进入企业告警或企业通知列表。每次 OPEN 保留记录，首次及超出冷却窗口时为指定平台运营员生成站内提醒。RECOVERED 独立记录，处置要求负责人先确认接手，再在恢复后结案。证据、游标和站内提醒在同一事务中落库。

验收顺序为证据读取及脱敏、数据库事务与重复导入、冷却边界、负责人及平台权限、前端站内提醒。部署及真实应用断网演练单独记录。

## 启用

1. 先将目标 MySQL 升级至 V23。ops 配置关闭应用自动迁移，按独立迁移流程执行。
2. 运行新版探针，使用仅探针账号可写且应用账号可读的 SQLite 文件及状态目录。SQLite 在探针写事务期间会使用同目录日志文件。保留原状态文件，替换或删除会导致导入停止。
3. 设置 `OPERATIONS_AVAILABILITY_ENABLED=true`、`OPERATIONS_AVAILABILITY_EVIDENCE_PATH`（绝对路径）、`OPERATIONS_AVAILABILITY_PORT`（默认 9093）和 `OPERATIONS_AVAILABILITY_OWNER_USER_ID`（启用的运营员账号 ID）。可用 `OPERATIONS_AVAILABILITY_COOLDOWN_SECONDS` 设置冷却，默认 300 秒。冷却基于故障确认时间，后续补读仍使用原证据时间。
4. 登录后打开 `/platform/availability` 查看全部故障或本人站内提醒。在应用无法服务期间仍可通过探针 CLI 查询本机证据。恢复后的首次可用扫描最多补读 100 条，后续继续读取。
5. 确认接手与结案动作只允许事件责任人发起。冷却抑制的事件仍可在全部告警中处置。配置负责人失效会暂停导入，需恢复其平台权限或配置新负责人后续跑。既有告警保留原责任账号，旧告警的处置仍要求原负责人具备平台权限。

## 验证结果

隔离 MySQL 8.4 应用 V1–V23。后端 600 项发现，553 项通过、47 项按环境开关跳过。新集成用例用 SQLite 测试证据覆盖重复导入、断档事务回滚、截断拒绝、冷却、本人提醒、负责人操作和停用运营员拒绝。Python 脚本套件 27 项通过，前端构建及 99 项前端契约测试通过。真实停机、登录后的浏览器联调及部署演练待执行。
