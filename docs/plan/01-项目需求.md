# EquipOps 项目需求文档

> 状态：规划稿，供需求评审；不是已实现功能清单。  
> 日期：2026-10-22  
> 项目定位：服务多家独立企业的工业设备运维与备件协同 SaaS。  
> 关联文档：[02-架构设计](02-架构设计.md) · [03-阶段路线与验收](03-阶段路线与验收.md)

## 1. 目标与边界

EquipOps 以“设备故障报修 → 派单 → 维修 → 备件领用／退回 → 验收 → 履历”为主线。短期交付可演示、可复测的多租户业务闭环；中期支持少量企业维修团队试用；长期在实际使用反馈和运维约束下评估正式运行。每个阶段都必须能独立演示、复现关键测试并说明仍未解决的限制。

本项目不以模块数量为目标。首版不做计费、企业自助注册、完整采购财务、IoT 实时采集、微服务拆分或孤立的 AI 聊天入口。HIS Agent 项目承担 Agent 应用能力展示；EquipOps 重点证明 Java 业务建模、事务一致性、授权和工程交付能力。

### 术语

- **租户**：一家独立企业。不同租户的数据必须隔离。
- **厂区**：租户内部的设备与工单管理范围；第一阶段每租户有一个默认厂区。
- **仓库**：租户内部的备件库存位置；第一阶段每租户有一个默认仓库。
- **全局账号**：人的登录身份，可加入多家企业；在任一时刻只以一个已授权租户身份发起业务请求。
- **成员关系**：账号在某租户内的状态、角色和后续厂区／仓库授权。
- **业务请求号**：客户端为一次业务动作提供的幂等标识；不同于服务器生成的流水编号。

## 2. 用户与权限

| 参与者 | 首版主要职责 |
| --- | --- |
| 平台运营人员 | 管理租户启停与异常处置；跨租户访问采用独立入口、最小权限和审计，不使用普通租户业务接口绕过隔离 |
| 企业管理员 | 管理本企业成员及其角色；不能管理其他企业 |
| 报修人 | 登记设备故障、查看授权范围内工单；可按规则参与验收 |
| 派单人 | 在授权范围内指定具有维修权限的负责人 |
| 维修人 | 接受工单、记录维修、领用／退回备件、提交验收；不能验收自己执行的工单 |
| 验收人 | 报修人或具有验收权限的主管；可验收通过或退回并填写原因 |

同一人可在不同企业拥有不同角色。用户选择当前企业后，服务端必须确认有效成员关系；请求体、URL 或请求头中的企业 ID 不能单独证明权限。撤销成员关系或角色后，不得继续执行原有操作。角色检查之外，还要检查对象所在租户、厂区和当前状态。

## 3. 第一阶段：可演示的多租户业务闭环

### 3.1 租户与基础资料

1. 至少可以准备两个测试租户；同一个账号可分别加入两者并显式切换。
2. 每个租户有默认厂区和默认仓库；后续允许在不重做库存模型的前提下增加厂区与仓库。
3. 设备编号、备件编号和业务请求号在适当的租户作用域内保持唯一；不同租户允许使用相同设备／备件编号。
4. 设备可登记、查询、修改和停用；设备归属不可越过当前租户。与未完成工单有关联的设备不得随意删除，具体停用规则以设计与测试为准。

### 3.2 工单闭环

首版工单状态沿用 `PENDING → IN_PROGRESS → AWAITING_ACCEPTANCE → COMPLETED`。派单本身不改变 `PENDING`，由负责人是否为空区分待派单和已派单；验收退回回到 `IN_PROGRESS`，并记录原因。取消工单暂不纳入首版，避免在规则未明确前加入状态。

1. 创建报修时，设备必须属于当前租户与授权厂区，创建人来自可信身份上下文。
2. 派单人只能派给本租户内有效且有维修权限的成员；重复或并发派单不得覆盖已成功派单结果。
3. 只有被授权的维修人可开始维修、记录处理结果并提交验收。
4. 验收人须为报修人或具有验收权限的主管；维修执行人不得验收自己的工单。
5. 每次状态变更与工单日志同时成功或回滚。非法跳状态、越权、重复提交和并发竞争均返回明确业务结果。
6. 工单详情可以按时间顺序展示处理履历，但日志、备注和详情同样受租户隔离约束。

### 3.3 备件与库存

备件目录描述“是什么备件”，仓库库存描述“在哪个仓库有多少”。首版只有默认仓库，但读写接口和流水必须明确仓库归属。

1. 入库、工单领用、未使用备件退回均生成不可直接删除的库存流水。
2. 领用数量必须大于零；工单与仓库必须属于同一租户；工单状态必须允许领料。
3. 库存不可为负。同一业务请求重试不能重复扣减，两个并发请求领用最后一件时最多一个成功。
4. 库存扣减、工单用料汇总和库存流水在同一数据库事务内提交；任一写入失败整体回滚。
5. 退回须关联原领用及原仓库，累计退回量不得超过累计领用量；不得以手工修改备件目录数量代替退回。

### 3.4 首版验收用例

- A、B 两个租户可以拥有相同的设备编号；A 通过列表、详情、猜测 ID、修改、工单、库存接口均不能读取或改变 B 的数据。
- 同一账号切换租户后只获得当前租户的角色和数据范围；撤权后原请求不能继续成功。
- 工单完整主线走通；非法状态、无权限、维修人自验收、并发派单均被拒绝并留下合理审计。
- 并发领用最后一件、重复请求、退回超量、流水写入失败等情形在真实 MySQL 环境下通过自动化测试。
- 前端使用真实 API 完成演示；数据库迁移、启动和测试步骤可由另一台环境复现。

## 4. 第二阶段：多厂区团队试用

第二阶段以第一阶段验收通过为进入条件，不按日历自动启动。核心增量只有三组：

1. **厂区／团队数据范围**：成员可被授予一个或多个厂区权限；设备、工单、统计、导出和后台任务均遵守该范围。转岗、撤权和跨厂区协作有明确规则与测试。
2. **租户内仓库调拨**：源仓申请／出库、在途、目标仓确认入库；跨租户调拨禁止。重复确认不重复入库，异常调拨可追踪与处理。库存余额与流水一致。
3. **恢复与值守**：定义备份策略并在隔离环境恢复；核对工单、用料与库存流水；监控接口失败、后台任务失败和库存异常，并有告警责任人、排查步骤与故障记录。

单租户恢复在共享数据库中是高风险操作：先恢复到隔离环境，验证该租户的完整关联数据，再设计受控回迁流程；不可在运行中直接删除并重导某租户数据。恢复时间与允许的数据损失目标需与实际试用团队共同确定。

## 5. 第三阶段：正式运行评估

第三阶段以真实试用反馈、数据规模和维护人员安排为依据，评估容量、升级回滚、安全审查、备份恢复目标、告警值守与必要的高可用措施。异步通知或外部系统对接确有需求时，再考虑 Outbox／消息队列；不能仅为增加技术栈而引入。

“可供真实企业正式使用”不是代码功能清单，而是经授权、隔离、恢复、监控和运维演练后形成的结论。未通过这些门槛时只能称为演示版或受控试用版。

## 6. 非功能需求与证明方式

| 属性 | 要求与证明方式 |
| --- | --- |
| 数据隔离 | 默认拒绝无租户上下文的业务读写；覆盖普通接口、分页、统计、导出、后台任务和日志；使用跨租户反例测试 |
| 一致性 | 状态条件更新、库存原子扣减、唯一约束、事务回滚与幂等；使用真实 MySQL 并发及故障注入测试 |
| 安全性 | 可信身份、租户成员关系、角色与资源范围校验；不在源码保留实际密码；审计管理操作 |
| 可追溯 | 工单状态日志和库存流水保留操作者、租户、请求号、时间与关联对象；敏感信息避免写入普通日志 |
| 可恢复 | 有备份、隔离恢复演练、数据核对和回滚步骤；正式目标值由试用团队确认，不预设虚构数值 |
| 可维护 | 单体按业务分包；数据库版本化迁移；明确 API 错误语义、测试和部署说明；避免未说明的双 ORM 混用 |
