## 2. 四张业务表

| 表 | 职责与关键约束 |
|---|---|
| alert_rules | 每企业固定规则唯一；阈值/窗口无默认值、必须显式确认，默认disabled；负责人有效管理员需业务验证 |
| alert_events | 人工状态与检测恢复状态独立；同企业+规则+错误码最多一个活动告警；结案open_slot=NULL允许新一轮事件 |
| alert_actions | 确认、备注、结案时间线，事务内与事件状态一起提交；不能替代M1统一审计 |
| alert_notifications | 企业/投递键唯一；DELIVERED代表站内提醒生成，不代表已读，更不代表管理员已确认 |

外键只约束本模块新增表，并含tenant_id防止跨企业关联；不修改现有users/成员/任务表。任务与企业、负责人有效成员/管理员关系在查询和写入时实时复核。Java Long对应BIGINT UNSIGNED，应用必须限制在Long正数范围内。

## 3. 为什么补充第5张证据表

只有occurrence_count/latest_task_id无法保证去重：两个实例可能同时扫描；ID大的任务可能先完成；告警结案后旧失败还在窗口中。为此草案增加alert_event_sources，唯一键(tenant_id,rule_id,task_id)。该表尚未新增Java实体，进入Mapper步骤时再按确定用途补充，不因此扩展当前业务实现。

未达触发阈值时，证据event_id可空；达到阈值后把未归属证据关联到活动事件。已归属旧事件的证据不能再次分配新事件。仅当成功插入新证据/成功认领未归属证据后才累计；重复键不能再次累加。证据插入、事件创建/合并、证据归属、计数和通知创建必须在同一短事务中组织，按规则行锁串行化同一企业规则的归并，不能只凭先查后插入避免竞争。

不能简单取最大task_id当扫描游标；后续按finished_at及ID分页、重复窗口补扫，证据唯一键兜底。暂不确认扫描频率/窗口阈值/冷却/恢复等待值；进入检测业务步骤时逐一确定，不写伪造默认规则或立即启动调度。

## 4. 状态及失败处理

OPEN→ACKNOWLEDGED→RESOLVED是人工处置状态；UNVERIFIED/RECOVERED是检测结果。确认不改恢复标记；人工结案条件和恢复依据仍需业务步骤确认，不能仅靠CHECK认为已满足。新故障应使活动事件恢复状态重新UNVERIFIED并清空recovered_at，同一事务更新。原失败任务永不因告警关闭而变SUCCEEDED。

动作使用expectedVersion条件更新，竞争失败409，回滚动作记录。非幂等备注后续若需防重复提交，应独立业务requestId唯一键；现有request_id只是追踪编号，不能冒充幂等实现。通知delivery_key包含事件/通知类别/接收者/冷却批次，不能每次重试生成新键。首版站内提醒可在事件事务内持久化，任何外部发送都不在此授权范围。

2. 第九步按企业/规则/故障类型读取活动事件和固定窗口内未归属证据。达到阈值前保留证据；已归属结案事件的证据不再触发。
