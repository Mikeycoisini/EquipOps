## 1. 总原则

每一阶段都交付一个可独立演示的纵向业务切片，而非一批尚未连接的空模块。阶段完成必须同时有：可运行流程、自动化反例测试、迁移与部署说明、已知限制，以及本人能解释的设计决定。下一阶段通过增量迁移和明确接口扩展，不推倒已交付的核心流程。

阶段名称：**S1 多租户业务闭环 → S2 维护巡检与设备备件协同增量 → 后续多厂区团队试用与正式运行评估**。进入下一阶段以验收证据为准，不以日期或代码量为准。具体工期在核对现有工程、数据库和个人可投入时间后估算；不预先承诺实际商用上线日期。

## 2. S1：多租户业务闭环（面试可展示）

### 交付范围与顺序

1. **基线审计**：确认当前数据库是否已有需保留数据；核对 Flyway、Entity、前端 API、配置与现有代码缺陷；为原有设备流程建立回归测试并移除源码中的实际密码默认值。
2. **租户与默认组织**：新增租户、成员关系、角色、默认厂区和默认仓库；完成登录后的企业选择与可信租户上下文。用增量迁移回填旧数据及仓库库存。
3. **设备与工单**：设备查询和修改按租户／厂区隔离；完成报修、派单、维修、提交验收、通过／退回及审计日志。落实维修人与验收人分离。
4. **库存一致性**：在默认仓库实现入库、领用、退回和流水；支持并发条件扣减、请求号幂等与事务回滚。
5. **整链交付**：用两个租户、多个角色跑前后端真实接口；整理自动化测试输出、演示步骤、部署说明和明确的限制清单。

### S1 结束门槛

- A/B 租户拥有相同资产／备件编号仍可分别工作；通过猜 ID、分页、修改等方式无法跨租户访问。
- 同一账号在两企业切换后只拥有当前企业授权；撤权后后续请求被拒绝。
- 工单主线走通；非法跳转、自验收、重复／并发派单被测试覆盖；状态与日志不会半成功。
- 真实 MySQL 上验证并发领最后一件、请求重试、退回超量及写流水失败回滚；库存与流水核对一致。
- 应用可通过文档在新的隔离环境运行；前端不以 Mock 数据掩盖未接通的业务功能。

### S1 可展示亮点与证据

**亮点**：共享表多租户隔离、按状态与角色控制的工单、仓库维度原子扣减／幂等／事务。  
**证据**：架构决策记录、状态／权限矩阵、Flyway 迁移、关键 SQL、跨租户与并发集成测试、完整操作演示。  

### 为 S2 保留的稳定边界

S1 每租户只有一个默认厂区／仓库，但设备、工单、库存与流水已有明确归属；备件目录与仓库库存已分开；用户权限已由租户成员关系承载。S2 增加厂区、仓库和权限范围时扩展这些模型，而不是重新定义库存真相或重写认证。

## 3. 原S2多厂区团队试用路线（后续规划）

### 交付范围与顺序

1. **厂区／团队授权**：成员可被授权一个或多个厂区；工单、设备、统计、导出、后台任务按厂区范围访问。转岗、撤权和跨厂区协作有明确规则。
2. **多仓库协同**：新增仓库及调拨状态；源仓出库、在途、目标仓确认入库均有租户范围与流水。重复确认、库存不足和中途异常能够识别、拒绝或受控处理。
3. **恢复与值守基础**：备份、隔离环境恢复演练、数据核对、关键指标和告警、故障处理手册。每项告警要有责任人、触发场景和演练记录。
4. **小范围试用**：使用虚构或经明确授权的试用数据；记录真实使用问题。正式收集企业数据前需确认数据责任、备份责任及授权范围。

### S2 结束门槛

- 两个以上厂区／仓库的测试场景通过；无权成员看不到或修改不了其他厂区业务数据。
- 调拨在正常、并发、重复确认、途中异常场景下可追溯；源仓、在途、目标仓余额与流水能核对。
- 在隔离环境实际恢复备份并核对工单、用料与库存；没有把“备份文件存在”当成恢复成功。
- 监控和告警能够发现一个预设故障，值守人员可按手册定位与处理。

### S2 可展示亮点与证据

**亮点**：租户内细粒度数据权限、跨仓库调拨状态与库存守恒、真实恢复与故障演练。  
**证据**：权限矩阵、调拨状态图及异常测试、库存／流水核对表、恢复演练记录、告警与故障处理记录。  
**表述边界**：试用版不等于正式商用；恢复目标和服务承诺必须在真实演练及团队约定后披露。

### 为 S3 保留的稳定边界

将业务流水、调拨、审计、请求关联标识和运维指标独立建模。后续有异步通知或外部系统集成需要时，可在不改变核心库存事务语义的前提下引入 Outbox；是否拆分租户数据库、高可用或消息队列由真实负载、合同与风险决定。

## 4. 第三阶段：现有业务可靠性与工程化（方向已确认，待S2验收后逐项设计）

用户于2026-10-31确认第三阶段路线为“业务范围适中、重点深化可靠性与工程化”。本阶段不以扩充菜单或新增大模块为目标；须等第二阶段逐项验收通过后再进入设计和开发。当前仅记录方向与验收标准，不代表已经实现，也不授权安装Redis、改造登录体系或批量开发。

### 目标方向

1. **并发一致性与幂等**：围绕现有库存、工单状态和维护执行登记，明确并发边界、重复请求语义、事务回滚与可追溯证据；用真实隔离数据库及并发场景验证。
2. **多租户权限验证**：基于现有租户成员、角色和业务归属，形成可复测的权限矩阵；覆盖猜测ID、列表/详情、写入、停用成员及企业切换，不改变既有业务规则来迁就测试。
3. **共享Session与双实例**：在单实例基线及部署配置核对后，设计Redis共享Session方案，并以两个应用实例验证登录、CSRF、企业上下文、登出和失效传播。只有设计评审和用户逐项确认后才引入Redis、改登录配置或迁移会话存储。
4. **基于测量的SQL与缓存**：先记录真实查询、数据规模和执行计划，再选择必要索引；缓存只用于有测量证据的热点读路径，并验证失效、租户隔离与一致性。不得为预想负载盲目加索引或缓存。
5. **日志、健康检查与恢复**：完善可关联请求的应用日志与健康检查；记录备份范围、责任和恢复步骤，在隔离环境实际恢复并核对业务数据。备份文件存在不等于恢复验收通过。

### 验收标准

- 关键状态变更和库存操作的并发、幂等、失败回滚场景有可复现测试与真实数据库证据。
- 租户/角色权限矩阵的允许与拒绝用例均通过，拒绝结果不泄露其他租户数据。
- 两实例验证证明Session与CSRF相关行为符合确认后的方案，实例重启、登出和会话失效结果可解释。
- SQL优化有优化前后数据规模、执行计划及测量记录；缓存（若有）通过更新、失效和跨租户隔离验证。
- 健康检查、日志定位、备份恢复均有操作记录；恢复后的关键工单、库存和流水核对一致。

### 保留的后续候选

原路线中的多厂区/团队权限、多仓调拨、恢复值守扩展继续作为后续候选，未删除也不自动并入本阶段；如实际需求明确，再单独评估依赖、范围和验收口径。

## 5. 后续正式运行评估与加固

S3 不再以增加菜单为目标。基于试用量和使用团队约定，完成容量基线、负载与故障测试、安全审查、权限复核、升级回滚演练、备份和恢复目标验证、值守交接及数据保留策略。只有当实际瓶颈或客户隔离要求出现时，才考虑独立数据库、消息队列、高可用部署或外部系统对接。

**可展示亮点**：把可靠性从“设计上应该可以”推进到“有测量、有恢复演练、有责任机制”。  
**证据**：运行与容量报告、故障演练、经同意的目标与实测结果、版本升级／回滚记录、安全问题整改清单。  
**终点判断**：实际团队负责人接受运行风险和操作手册，并完成约定的验收；不能由项目作者单方面宣布“企业级生产可用”。

## 6. 跨阶段不返工约束

| 决策 | S1 做法 | 后续如何扩展 |
| --- | --- | --- |
| 租户模型 | 全局账号＋成员关系；每请求可信当前租户 | 增加厂区／仓库授权，不把租户 ID 当自由传入的参数 |
| 库存模型 | 备件目录与仓库库存分离，默认仓库 | 增加仓库与调拨，无需把全局库存数拆开重做 |
| 数据迁移 | Flyway 增量变更与旧数据回填；不改 V1 | 每阶段新迁移先在副本验证，保留数据核对与回退步骤 |
| 工单规则 | 明确状态、角色、条件更新和日志 | 新状态须同步修改状态矩阵、迁移和测试，不靠字符串硬编码绕过 |
| 流水与幂等 | 请求号、原领用引用、仓库和租户均可追踪 | 调拨、异步事件与审计复用同一关联标识，不复用错误语义 |
| 接口与前端 | 先核对既有 API 契约，再稳定第一阶段接口 | 后续新增字段和接口尽量兼容；不以大规模重写前端适配后端 |

## 7. 每阶段收尾材料

每一阶段结束时在仓库留存：

1. 版本范围及状态说明：完成、未完成、已知限制。
2. 设计决策与关键取舍：为什么采用此状态机、隔离或事务方案。
3. 自动化测试与人工演示步骤：至少一条正常链和一条关键失败链。
4. 迁移、部署及恢复／回退说明：下一阶段从这个版本继续，而不是重建环境。

下一步是在用户审阅本组需求与设计文件后，才将 S1 拆成可执行的逐项实施计划。当前文档不授权批量改写后端业务代码。
