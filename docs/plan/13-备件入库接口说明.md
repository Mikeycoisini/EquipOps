# 备件入库接口说明

日期：2026-10-27。源码实现说明；不是数据库迁移、真实事务/并发或前端整链验收记录。

## 调用契约

`POST /api/inventory/stock-ins`，沿用 Session 登录、CSRF 请求头和活动企业选择。

- 当前企业成员必须具有 `TENANT_ADMIN`，沿用备件目录管理权限；其他角色不能因此获得入库资格。
- 请求头 `Idempotency-Key` 必填，为 1..64 位 ASCII 字母、数字、横线或下划线，区分大小写。客户端应在一次动作开始时生成，网络重试沿用原值；新动作使用新值。
- 请求体仅包含 warehouseId、sparePartId、quantity、referenceText、note，不接收可信企业/操作人/库存余额或交易类型。

```json
{
  "warehouseId": 10,
  "sparePartId": 20,
  "quantity": 2.5,
  "referenceText": "采购单-1",
  "note": "验收入库"
}
```

示例 ID 需替换为实际企业内有效数据。返回 `Result<InventoryTransactionVO>`，包含数据库流水 ID/编号、requestId、仓库/备件、本次增加数量、操作人和创建时间；本次 quantity 不表示仓库最终余额。

## 业务与幂等

1. 重新验证企业成员及管理员权限，校验 ID、正数量、最多11位整数/3位小数和文本长度。
2. 根据当前企业和请求号读取成功流水。相同操作人、仓库、备件、数值相等的数量、相同单据说明和备注才能重放原结果；不同操作人、不同内容或其他命令类型返回409。文本 null 与空字符串视为不同内容，不静默改写请求。
3. 新请求才锁定并检查同企业仓库/厂区和备件的启用状态。按仓库/厂区、备件的顺序加锁至事务结束；S1 采用较粗仓库锁，同仓库多笔入库可能串行，后续有吞吐需求再优化。
4. 先保存固定 INBOUND、MANUAL 类型的流水，以企业内唯一请求号取得执行资格。并发唯一键冲突后使用 FOR UPDATE 当前读，避免读取先前快照而漏掉已经成功的事务；不是本请求的唯一键冲突不能包装为成功。
5. 首次建账从零余额和零安全库存开始，已有记录保留原阈值；通过 SQL 的 quantity = quantity + 本次数量 原子增加，不写回旧数量。上限为99999999999.999，超限拒绝。
6. 流水、建账、加量和返回前重查处于同一事务。写入失败或影响行数异常抛出异常，由事务回滚，不留下半笔库存和流水。锁冲突返回409，可用原请求号重试。

快速重放发生在当前角色校验之后、资源启用检查之前，所以撤销管理员权限后不能重放；已完成请求不会因仓库后来停用而再次执行或额外加库存。

## 数据库与验证边界

- 本轮只生成 V6 文件，不执行迁移、不启动应用、不读写真实业务库。V5/V6 是否已在用户数据库执行，需另外核对 Flyway 历史。
- V6 只新增可空 request_id 与企业内唯一键，旧流水保持 NULL，不回填、不删除、不修改 V1..V5。
- 新的流水 Entity 已包含 request_id；部署此版本前必须确保目标库已应用 V6，否则现有流水查询也可能因缺少该列失败。应用启动可能自动执行待应用 Flyway 迁移，执行前先核对 schema 和备份。
- 不使用或搬运 spare_parts 的旧库存及安全库存。首次仓库建账的阈值0来自余额表默认规则，后续安全库存维护另行设计；工作台低库存汇总仍未接入。
- 库存写入与请求冲突等单元测试使用内存数据库边界替身；它们不等于真实 MySQL 回滚或并发验证。MyBatis 测试验证生成 SQL 和参数；独立 MVC 测试未加载 Session/CSRF 安全链。
- 下一步在隔离数据上验证：同请求并发、不同请求同时加同一余额、首次并发建账、超上限、库存写失败回滚、跨企业访问、角色撤销及 Session/CSRF。前端入库页面尚未接入。
