# 工单验收通过接口

日期：2026-10-27。后端项目：D:/Opus/EquipOps。

## 接口与流程

- 请求：`POST /api/work-orders/{id}/approve`，无需请求体。
- Controller：`WorkerderController.approve`。
- Service：`WorkOrderService.approve`，实现位于 `WorkOrderServiceImpl.approve`。
- 更新 Mapper：`WorkOrderMapper.approveWorkOrder`，SQL 位于 `mapper/WorkOrderMapper.xml`。
- 返回：`Result<WorkOrderVO>`，包含最新 `COMPLETED` 状态与 `completedAt`。

登录后选择当前企业，再通过现有 Session 和 CSRF 机制调用接口。
方法取得当前用户和当前企业角色，以企业 ID + 工单 ID 锁定工单。
只有 `AWAITING_ACCEPTANCE` 工单可以通过验收；维修负责人不能验收自己的工单，
即使同时是报修人或具有 `ACCEPTOR` 角色也不例外。
其余人员须为报修人（`created_by`），或拥有当前企业的 `ACCEPTOR` 角色。
企业管理员不会自动获得验收资格。

SQL 同时限定企业、工单 ID、原状态和非本人维修，更新状态并使用数据库当前时间写入
`completed_at`。随后插入一条 `STATUS_CHANGED` 日志，状态为
`AWAITING_ACCEPTANCE → COMPLETED`，标题“验收通过”，`actor_user_id` 记录验收人。
验收人保存在日志中，`assignee_user_id` 仍表示维修负责人。
状态、完成时间和日志位于同一个事务，任何一步失败均抛异常回滚。
最后重新查询工单，返回数据库中的最新状态和时间。

## 角色登记与授予

`V4__register_acceptor_role.sql` 只登记 `ACCEPTOR` 角色；已有同编码记录时跳过，
不覆盖角色资料，不自动给用户授权。Flyway 会在数据库连接可用的启动过程中执行待应用迁移。
本次开发未运行该迁移，也未修改真实数据库。

需要手动登记时，在确认目标 schema 是 equipops 后运行该脚本；保留迁移文件，
以后 Flyway 执行时会识别已存在的角色。不要修改已执行的 V1～V3 文件。
登记后只读查询角色 ID：

```sql
SELECT id, role_code, name FROM roles WHERE role_code = 'ACCEPTOR';
```

企业管理员调用现有 `PUT /api/tenant-members/{id}/roles`，把上面的角色 ID 加入
该成员的角色集合。路径中的 id 是成员关系 ID，不是用户 ID；该接口替换整组角色，
需要保留的原有角色 ID 也必须一并提交。授权写入当前企业的 `tenant_member_roles`，
不使用全局 `user_roles` 授予企业验收资格。

可授予角色的默认配置已包含 `TENANT_ADMIN,ACCEPTOR`。若部署环境显式配置了
`equipops.tenant.grantable-role-codes`，需在原有值上追加 `ACCEPTOR`，保留其他已配置角色。
