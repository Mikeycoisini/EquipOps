# 第三阶段：可靠性与Java工程能力深化

确认日期：2026-11-02。用户确认保持单体架构，按并发可靠性、Redis共享Session、线程池与异步任务、IO及性能诊断方向逐项推进。本文是范围与顺序约定，不代表各项设计已完成或已有实现。

## 一、架构与协作边界

- 保持单体应用，可以运行多个相同实例；不拆微服务。先检查模块依赖，必要调整逐项说明，不批量重构包和方法。
- 沿用现有Session登录、企业上下文和数据库事务规则。Redis共享Session不代替实时权限校验。
- 第二阶段首轮报告证明核心接口通过；完整浏览器流程、扫码返回及其他未测项继续保留，不宣称第二阶段全部验收完成。用户已授权启动第三阶段规划，按小步推进并持续处理相关遗留项。

## 三、按证据决定的可选项

- 统计缓存：仅有测量依据后选择少量热点，明确企业/参数隔离、时效和失效规则；库存写入不以缓存为准。
- 模块依赖检查工具：根据现有包结构评估，不自动引入Spring Modulith或调整项目结构。
- SSE：仅当任务进度交互确实需要时选择，不默认追加WebSocket。
- NIO原理可通过独立小实验学习。当前无设备采集业务需求，不把Netty/TCP采集、协议、心跳、重连加入主项目；后续若提出需求再单独设计。
- 不引入消息队列、分布式事务框架或微服务基础设施来凑技术数量。

## 四、首个实施单元

先只读回顾现有领料入口、事务、锁顺序、条件扣减、幂等与流水，然后设计“两个或多个独立请求同时领最后一件”场景。并发请求须使用不同请求号，避免把重复请求验证误当库存竞争；同号重试另设场景。

核对当前测试库身份与已有数据，准备独立标记数据、初始快照和核对规则后再执行。预期是最多一次有效领料、最终余额为零，失败请求不会留下用料或流水；具体HTTP状态遵循已有契约。若成功数为零，必须说明原因，不能判为通过。完成此项后再进入下一单元，不批量补齐所有测试和业务。
