# A8 外部可用性探针

第一项交付用独立进程访问 ops 管理端口的 `/actuator/health`。仅 HTTP 200 且顶层状态为 UP 算作成功。连接失败、超时、异常 HTTP 状态和无法解析的响应分别保留为枚举证据。探针固定访问本机管理端口，忽略代理和重定向。操作员在应用进程之外运行探针。

连续三次故障开启事件，连续两次成功恢复。事件开启时间为第三次失败采样的完成时间。同一故障期间只保留一个开启事件和一个恢复事件。每个目标使用独立 SQLite 文件，持久状态和事件同事务提交，重启继续计数。状态中记录最近采样时间、结果和连续次数。只保存固定代码，禁止记录响应正文、请求凭据、异常细节。

1. 用真实回环 HTTP 服务验证 UP、DOWN、错误响应与拒绝重定向。
2. 验证状态持久化、故障去重、连续成功恢复和重复运行期间的采样串行化。
3. 在运维文档提供启动、查询和停机演练命令。
4. 后续交付平台固定规则、负责人、通知与处置接口。探针证据只供操作系统授权的运维主体查询。

## 本机演练

需要 Python 3.9 或更新版本。连接和 HTTP 交换各有 2 秒超时。 先以 `ops,redis-session` 启动应用。探针与应用共享主机网络命名空间，通过 ops 管理端口访问健康响应。给探针准备仅运维账户可写的目录。由应用之外的进程管理器监督探针，并为每个端口配置一个定期采样进程。

```bash
install -d -m 700 "$HOME/.equipops-probe"
python3 scripts/availability_probe.py run --port 9093 --interval 10 --state "$HOME/.equipops-probe/9093.sqlite"
```

在另一终端查看最近一次状态和最多 100 条事件。

```bash
python3 scripts/availability_probe.py status --port 9093 --state "$HOME/.equipops-probe/9093.sqlite"
```

演练时停止应用，等待探针记录三个连续故障样本，检查 OPEN 事件。恢复应用及其依赖，等待两个连续 UP 样本，检查 RECOVERED 事件。前台探针可用 Ctrl+C 停止，再用同一状态文件续跑。定期采样会跳过距离上一次完成时间不足配置间隔的轮次。手工 `sample` 每次都计入状态转移，应在同一目标的定期采样停止后用于调试。

此探针覆盖应用端口失联和健康端点自身已报告的依赖状态。主机整体掉电或网络命名空间不可达需要主机外的监控。SQLite 文件应放在本地文件系统，按运维要求归档，当前实现保留历史事件。

## 验证结果

Python 脚本套件 26 项通过，含探针 6 项。独立进程使用临时状态文件完成回环演练，从目标端口拒绝连接到健康响应恢复，恰好产生一条 OPEN 和一条 RECOVERED。演练目标为测试 HTTP 服务。真实 EquipOps、MySQL/Redis 断连与部署验收待执行。
