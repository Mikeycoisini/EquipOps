## 二、问题与修复

### 1. Flyway版本冲突

用户日志显示Found more than one migration with version 13。新副本的V13__create_audit_events.sql与V13__create_monitoring_alert_tables.sql重复。

在V2副本中保留告警V13、续扫V14，将审计迁移改名为V15__create_audit_events.sql。审计SQL内容字节保持不变。新库从V1顺序执行至V15。该映射适用于本次新建V2库，旧库升级需另核对自身历史。

先用静态检查记录重复V13，再修复为15个唯一版本。执行clean package清除复制遗留的target资源，打包JAR中核对无旧审计V13。

### 2. 旧默认数据库与运行资源

V2的application.properties改为默认equipops_v2、端口8082、独立导出目录和会话Cookie。数据库用户名读取DB_USER并默认root，密码读取DB_PASSWORD，原密码默认值已移除。IDEA当前主运行配置已有DB_PASSWORD，可继续用于本机连接。

Flyway baseline-on-migrate设置false，保持validate-on-migrate与clean-disabled。默认激活redis-session，Redis命名空间默认equipops:v2:session，Cookie为EQUIPOPS_V2_SESSION。

ops配置默认业务端口8082、管理端口9093，沿用显式DB_URL/DB_USER/DB_PASSWORD要求。

### 3. 主类遗漏Mapper扫描

处理迁移后，完整启动复现AlertEventMapper无法注入。主类原有显式MapperScan只包含audit等包，遗漏operations。在新V2主类保留原列表并加入com.operations.mapper，完整启动复验通过。

### 4. 前端配套连接

仅在新V2前端的vite.config.ts中将开发端口改为5174、/api代理改到http://localhost:8082，避免与旧版默认端口重合。前端构建通过。

## 五、本机启动方法

1. 启动MySQL及本机Redis，默认Redis连接127.0.0.1:6379。Redis有密码时设置匹配的REDIS_PASSWORD，无密码时使用空密码配置。
2. 在新V2后端IDEA工程运行com.EquipOpsApplication，保留现有DB_PASSWORD环境变量。默认DB_URL为equipops_v2；如自行设置DB_URL，核对其目标库。
3. 后端地址为http://localhost:8082。ops配置启动时明确设置V2的DB_URL、DB_USER、DB_PASSWORD。
4. 在新V2前端运行npm run dev，打开http://localhost:5174。
5. 下一步初始化新库管理员、企业和必要基础角色，再开展实际登录及业务联调。

默认导出根为用户主目录下.equipops-v2/inventory-exports，可用INVENTORY_EXPORT_ROOT覆盖为V2专用绝对路径。
