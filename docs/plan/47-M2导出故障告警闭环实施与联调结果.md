## 2. 整体执行顺序

1. 管理员配置当前企业规则，明确开关、失败次数阈值、统计窗口、通知冷却和负责人。
2. 显式开启后台调度后，按固定延迟调用检测方法。
3. 先选择最久未成功扫描且配置、企业与负责人有效的规则。本轮最多100条规则、合计100批任务，每条规则最多3批，每批任务100条。
4. 取得数据库观测时间，读取续扫记录。未完成且规则版本一致时继续原固定窗口，否则重新建立统计窗口。
5. 按 finished_at 与 taskId 读取失败任务，每批先检查中断和额度，再在短事务内锁定规则并复核版本、资格与续扫位置。
6. 对可信失败任务插入去重证据，按错误类型合并活动事件，达到阈值才创建事件。只有成功认领的证据增加次数。
7. 使用冷却时间、稳定投递键和接收者最新资格生成站内提醒。证据、事件、提醒和续扫位置同批提交，失败整批回滚。
8. 独立检测恢复。最后新故障之后经过完整统计窗口、窗口内没有同类型失败且出现后续成功导出，才写入 RECOVERED。
9. 管理员查询告警，填写说明后确认接手、保存备注、人工结案。每次操作使用 expectedVersion，状态与处置记录同事务保存。
10. 负责人查看本企业本人收到的站内提醒，阅读操作幂等设置首次已读时间。

人工状态 OPEN → ACKNOWLEDGED → RESOLVED。检测状态 UNVERIFIED / RECOVERED 独立保存。人工结案保留原检测状态，新故障使活动事件恢复为 UNVERIFIED。

## 4. 接口清单

所有接口采用现有 Session、CSRF、企业上下文和管理员权限校验。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | /api/operations/alerts | 企业告警分页及状态筛选 |
| GET | /api/operations/alerts/{id} | 当前企业告警详情 |
| GET / PUT | /api/operations/alert-rules/export-failures | 读取、创建或按版本更新固定规则 |
| GET | /api/operations/alerts/{id}/actions | 最近200条处置记录 |
| POST | /api/operations/alerts/{id}/acknowledge | 确认接手 |
| POST | /api/operations/alerts/{id}/notes | 保存备注 |
| POST | /api/operations/alerts/{id}/resolve | 人工结案 |
| GET | /api/operations/notifications | 本企业本人已投递提醒分页 |
| POST | /api/operations/notifications/{id}/read | 幂等标记已读 |

处置请求包含 expectedVersion 和 note。规则创建不传 expectedVersion，更新必须传查询得到的版本。规则范围为阈值1—10000、窗口1—86400秒、冷却0—86400秒。负责人必须是本企业账号、成员关系均有效的管理员。非法参数400，越权403，其他企业或其他接收者对象404，版本或状态冲突409。

## 6. 启用方法

1. 核对将要连接的数据库，先按项目既有 Flyway 流程应用到 V14。使用关闭自动迁移的部署配置时，先完成独立迁移再启动应用。
2. 在后端启动环境中设置 `OPERATIONS_ALERTS_ENABLED=true`，再启动或重启后端。
3. 默认每次完成后延迟30000毫秒再执行，首次延迟10000毫秒。可通过 `OPERATIONS_ALERTS_DELAY_MS` 和 `OPERATIONS_ALERTS_INITIAL_DELAY_MS` 调整。
4. 使用企业管理员登录前端，在“告警与处置”中配置并开启企业规则。
5. 本企业窗口内的受支持系统错误达到阈值后，查询事件及负责人的站内提醒。

自动调度默认关闭是本轮采用的运行策略。页面初次显示的阈值3、窗口600秒、冷却300秒仅是待确认的填写建议，保存前不会创建规则。

识别 TIMEOUT、WORKER_LOST、IO_FAILED、QUERY_FAILED、DISK_LIMIT。规则负责人资格失效后跳过扫描与提醒，重新配置有效负责人后继续。当前策略保留规则开关，便于管理员发现并修复配置。

## 8. 当前边界和后续工作

本轮交付导出任务系统故障告警闭环。应用整体宕机、Redis/MySQL不可达等外部可用性告警仍需独立探针或监控系统接入。应用内调度依赖应用和数据库可用。

扫描使用规则回溯窗口，持久化进度用于固定窗口续扫及失败重试。长期停机超出窗口的历史故障没有全量补偿保证。每次读取窗口内待归属证据仍可能较多，本轮未开展生产规模容量实验。验证未覆盖长时间停机、生产数据规模、完整灾备或远程M1分支合并。

站内提醒保存在当前数据库，当前没有外部短信、邮件或即时通信投递。恢复判定采用完整窗口无同类失败并有后续成功任务的保守策略，成功证据不足时继续显示待确认。

建议下一步由用户用自己的企业配置一个有效规则，按报告启用后台扫描，完成一次可观察的故障演练。外部可用性监控可作为之后的独立功能项。
