# Session 认证与当前企业上下文

本次用户明确授权完成所有认证前置实现。采用 Spring Security 7（版本由 Boot 4.0.6 管理）、数据库账号和 BCrypt、服务端 HttpSession。只实现认证前置，不填充企业、成员、厂区、仓库 CRUD 的空方法，不改同学写的工单业务或原有设备业务。

## 一、接口及使用顺序

| 接口 | 说明 |
| --- | --- |
| GET /api/auth/csrf | 匿名可获取当前会话 CSRF，返回 headerName/parameterName/token |
| POST /api/auth/login | account/password，成功响应 userId/account/name，通过 JSESSIONID Cookie 保存登录 |
| GET /api/auth/me | 当前有效用户及当前企业、成员、实时企业角色；没有选择企业时企业为空 |
| POST /api/auth/active-tenant | tenantId 仅是选择意图，校验企业和成员关系后写入 Session |
| POST /api/auth/logout | 失效安全上下文、Session、CSRF 和 JSESSIONID Cookie |

1. GET csrf，保存响应 Cookie；POST login 同时携带 Cookie 及返回的 CSRF 请求头。
2. 登录后会更新 Session ID 并清除旧 CSRF，重新 GET csrf。
3. GET me 验证身份；再以新 CSRF POST active-tenant。该企业须已存在、启用，且当前账号有启用的成员关系。
4. 后续请求携带同一会话 Cookie；所有 POST/PUT/PATCH/DELETE 附带当前 CSRF 请求头。
5. 退出后再次登录前，重新获取 CSRF。

不返回或使用 Bearer token。LoginResponseVO 的 token 字段已移除；原前端令牌登录契约尚未适配，本次不修改暂停中的前端认证页面。Vite /api 代理可维持同源 Cookie；若以后改为跨域，需明确配置可信来源、凭据和 Cookie 策略，不能放开任意来源。

## 二、业务怎样使用

- CurrentAccessService.requireEnabledUserId()：认证主体必须是服务端 LoginUser，重新查询 users.enabled，失效返回 401。
- requireActiveTenantId()：查询会话中的企业选择，验证企业和成员关系；未选择返回 409，无有效成员关系或企业不可用统一返回 403。
- requireTenantAccess()：同时返回当前企业、成员关系 ID、实时 roleCodes。
- requireTenantAdminTenantId()：以上验证后必须含 TENANT_ADMIN，返回当前企业 ID。
- validateTenantSelection(tenantId)：用于企业切换，只验证选择，不直接信任客户端 ID。

同次请求固定企业选择，避免其他标签页的切换改变正在执行请求的企业 ID；后续请求重新核验账号、成员和角色。没有使用跨请求的角色缓存，也没有在 ThreadLocal 中自行存储企业上下文。

企业管理员的角色编码约定为 TENANT_ADMIN。该角色定义及与成员的关联必须由受控初始化真实建立；本次不自动创建角色、账号、企业或成员。user_roles 不作为企业角色依据。

## 三、安全链范围和仍未完成的事项

- /api/auth/csrf GET 与 /api/auth/login POST 允许匿名；其余 /api/** 必须登录。写操作保留 CSRF；未登录的无 CSRF 写请求可能先返回 403，这是 CSRF 过滤器的预期顺序。
- 每个受保护请求重新核对账号状态。tenant-members 路径再检查当前企业管理员权限；sites/warehouses 路径再检查有效当前企业。
- 认证入口采用与现有 Result 一致的 JSON 错误；异常处理只覆盖认证 Controller，不改变旧业务异常语义。
- 密码哈希不输出、不进入 toString；认证成功后擦除认证主体中的密码哈希。
- 用户创建接口现在也要求登录；首次账号不能通过开放注册绕过认证。新空库需用受控初始化建立账号及 BCrypt 密码哈希，不提供默认密码或自动管理员。
- 账号密码变更后的所有会话批量撤销、登录限流、企业初始化、旧业务租户迁移和动作级角色矩阵尚未实现，后续单独推进。
