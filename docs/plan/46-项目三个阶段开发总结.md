# EquipOps 项目三个阶段开发总结

整理日期为 2026-11-08。

本文汇总 `docs/plan` 中历史 S1、S2、S3 的目标、实现成果、验证证据及遗留事项，并参考已有联调报告和当前接口源码。阶段状态按最新专项记录解释，历史文档中“下一步”“尚未实施”的表述保留其当时语境。本文整理已有成果，本次未重新执行接口测试或数据库核验。

## 一、三个阶段总览

| 阶段 | 核心目标 | 主要交付 | 当前结论 |

## 二、第一阶段 S1——多租户业务闭环

### 1. 阶段目标

建立能实际演示的企业设备运维流程。用户登录并选择企业后，在当前企业内完成设备管理、报修维修、验收及库存流转，保证业务数据具备明确归属。

### 2. 主要成果

| 业务模块 | 已交付内容 |
| --- | --- |
| 认证与企业上下文 | Session 登录、CSRF、企业选择及切换，服务端提供可信当前企业上下文 |
| 企业成员与角色 | 成员管理、角色分配及管理员权限控制，业务访问结合当前成员关系校验 |
| 设备管理 | 设备档案、状态、维修履历及设备关联工单查询 |
| 工单闭环 | 报修、派单、开工、维修记录、提交验收、通过及退回，保留操作人、原因和时间线 |
| 库存业务 | 备件目录、仓库余额、入库、工单领料、退料和库存流水 |
| 查询与工作台 | 工单与流水分页详情、原领料追溯、低库存统计及安全库存阈值维护 |
| 基础组织增量 | 保留用户已完成的厂区详情、创建、修改及仓库创建能力 |

### 3. 关键业务设计

1. 企业归属由服务端上下文确定，查询和修改均携带企业条件。
2. 全局账号通过企业成员关系取得当前企业身份与角色。
3. 工单按状态和角色流转，维修人与验收人分离。
4. 备件目录与仓库实际余额分开，库存变化通过事务和流水追踪。
5. 领料使用条件扣减及请求号幂等，退料关联原领料并限制累计退回数量。

这些边界为后续维护、统计和导出提供了统一业务基础。

### 4. 验收与证据

- 20 号记录保留用户于 2026-10-29 确认“前后端全部功能测试通过”的反馈，S1 据此标记功能验收通过。
- 该阶段记录了 146 项非数据库回归通过，以及隔离测试库、真实 HTTP 和前端联调情况。人工反馈未逐项附完整运行证据，引用时应保留这一范围。
- 原 S1 计划 38 项接口，加设备关联工单、流水详情、安全库存阈值维护 3 项，按当时口径共 41 项。额外组织管理入口单列，此数值用于历史范围说明。
- 最后一件竞争、动态撤权、事务故障回滚等专项证据随后在 S3 补充，分别引用对应报告。

### 5. 阶段价值

S1 将设备、工单、用料、余额和流水连接起来，能够说明一次维修如何影响业务状态和库存，以及如何追溯操作责任。

主要依据为 [20-S1阶段总结与S2启动](20-S1阶段总结与S2启动.md)、[16-S1接口完成度与退料代码说明](16-S1接口完成度与退料代码说明.md)及 05—19 号相关实施记录。

## 三、第二阶段 S2——维护巡检与设备备件协同

### 1. 阶段目标

在既有设备与工单基础上增加日期周期维护、设备与备件适配关系、设备二维码及维修统计，支持计划性维护和日常查询。

### 2. 接口与页面成果

| 方向 | 主要能力 | 新增接口数 |
| --- | --- | --- |
| 维护计划 | 创建、分页、详情、启停、修改 | 5 |
| 维护执行 | 登记执行结果、执行历史分页、执行记录详情与快照 | 3 |
| 设备备件适配 | 添加关系、正向查询、解除关系、从备件反查设备 | 4 |
| 维修统计 | 报修排行、每日新增与完成趋势、平均总处理时长、逾期汇总 | 4 |
| 合计 | 以 24 号清单的新增路由口径统计 | 16 |

已有接口增加 `dueOnly` 和 `overdueOnly` 两项筛选。设备二维码由前端生成设备链接，复用设备详情接口。

### 3. 已明确的业务规则

- 维护按日期周期到期，支持负责人登记本期执行结果，并保留历史快照。
- 执行登记使用请求号处理重试，竞争同一期时只能产生一次有效执行及周期推进。
- 设备与备件适配关系保留历史可见性，停用备件和停机设备的既有关系仍能查询。
- 统计中的平均时长是工单创建到验收完成的总处理秒数，展示同时包含样本量。
- 逾期查询按服务端时间与截止时间判断，并与其他查询条件组合。
- 日期维护首版保留明确边界，运行小时触发、混合触发和自动生成维修工单属于后续候选。

### 4. 实际验证

26 号首轮验收记录了以下结果。

1. 在 `equipops_test` 应用 V8—V10，完成维护计划、维护执行及适配关系表的隔离环境验证。
2. 16 条新增路由均有真实 HTTP 调用记录，覆盖核心正常流程及关键反例。
3. 两企业四项统计与原始工单数据核对一致。
4. 浏览器验证维护详情、历史快照、统计、备件反查、设备跳转、二维码弹窗及临时适配解除。
5. 当次 345 项非数据库回归通过，真实数据库结果另行记录。

### 5. 遗留验收事项

按 26、27 号记录，仍需保留维护前端写入与重试整链、完整浏览器角色/跨企业分享链接、真实手机扫码及打印等验收尾项。不同请求号维护竞争及部分权限场景后来已在 S3 补测，完整参数矩阵、午夜边界及全部故障场景仍以专项证据为准。

S2 可表述为“业务代码和首轮核心联调已完成，完整阶段验收仍有尾项”。

主要依据为 [24-第二阶段范围与接口实施清单](24-第二阶段范围与接口实施清单.md)、[26-第二阶段首轮隔离环境验收](26-第二阶段首轮隔离环境验收.md)及 21—25 号设计说明。

## 四、第三阶段 S3——可靠性与 Java 工程能力

### 1. 阶段目标

保持 Java 单体架构，围绕已有业务深化并发一致性、实时权限、共享会话、异步任务、文件 IO、SQL/JVM 诊断与恢复能力。27 号已记录用户授权启动本阶段，同时继续保留 S2 尚未完成的验收事项。

### 2. 并发、幂等与事务回滚

28 号报告汇总了七项核心场景的通过证据。

| 场景 | 验证内容 |
| --- | --- |
| 不同号竞争最后一件 | 只有一次有效领料，余额与流水保持一致 |
| 同号并发与重试 | 返回同一流水，库存及用料只发生一次效果 |
| 同号修改数量 | 拒绝冲突内容，原业务结果保持一致 |
| 并发退同一笔领料 | 限制累计退回量，只留下有效退料 |
| 并发派单 | 只有一个负责人和对应派单日志生效 |
| 不同号竞争维护同一期 | 只登记一次执行，下次到期只推进一次 |
| 写入中途故障 | 已发生的扣库存和插流水随事务回滚，解除故障后可重试 |

七项证据来自分次执行记录，其中后四项有最终整组通过记录。故障注入还核对了目标事务确实到达指定位置及测试资源清理结果。

### 3. 多租户权限与共享 Session

- 30 号记录后端六项核心权限场景通过，覆盖成员停用、管理员撤权、跨企业读写、普通成员管理限制和企业切换。
- 前端记录 36 项契约测试通过，并实际观察 A→B→A 企业切换后的数据与菜单角色变化。
- Redis 共享 Session 延续现有登录、CSRF 和企业上下文机制，数据库实时授权检查继续生效。
- 33 号记录双实例、Redis 停止/恢复、会话保留/丢失及跨实例撤权实验。首轮 31 项中有 1 项“恢复后首请求立即成功”失败，后续专项 8 项通过，确认自动重连后的恢复行为。
- Redis 故障时的响应体验、生产高可用、负载均衡及 HTTPS 等验证仍按该报告的限制记录。

### 4. 库存流水 Excel 异步导出

当前源码已有五项接口。

| HTTP 方法与路径 | 功能 |
| --- | --- |
| `POST /api/inventory/exports` | 提交导出任务 |
| `GET /api/inventory/exports` | 分页查询本人任务 |
| `GET /api/inventory/exports/{id}` | 查询任务详情和状态 |
| `GET /api/inventory/exports/{id}/file` | 下载生成文件 |
| `POST /api/inventory/exports/{id}/cancel` | 取消排队或执行中的任务 |

主要实现包括以下内容。

1. 使用数据库持久化任务归属、筛选条件、进度、状态、租约及文件元数据。
2. 使用有界线程池，配置为最多 2 个执行线程和 10 个排队任务，并处理拒绝、取消、超时与失联恢复。
3. 后台根据可信任务身份重新校验权限，分批读取流水并逐步生成 XLSX。
4. 临时文件写完后发布正式文件，配合任务条件更新和失败清理控制生命周期。
5. 下载重新检查企业、创建人、角色、任务及文件状态，并增加路径安全、并发名额、非阻塞传输及超时释放。
6. 查询、创建/后台执行与下载/取消按当前分层组织，取消与下载位于同一业务实现类。

V11 用于创建导出任务表，V12 为本人任务列表增加 `(tenant_id, created_by, created_at, id)` 索引。迁移执行范围应查对应记录，各环境版本需分别核对。

### 5. 固定规模 SQL、内存与线程池实验

| 实验 | 条件与记录结果 | 解释范围 |
| --- | --- | --- |
| SQL 基线 | 合成流水 12.5 万条、任务 1 万条，采集执行计划与重复测量 | 用于定位特定分布下的扫描、排序和分页成本 |
| XLSX 单任务 | 10 万行，最大堆 96 MiB，记录耗时 2.808 秒、采样堆峰值约 29.62 MiB | 当前写入组件的一次测量结果 |
| XLSX 双任务 | 每任务 10 万行，记录总完成时间 2.884 秒、采样堆峰值约 61 MiB | 支持该夹具下受限堆内完成，进程总内存另计 |
| 线程池容量 | 提交 14 个受控任务，2 执行、10 排队、2 拒绝 | 验证容量边界 |
| 索引对照 | 多轮 A/B 比较，并补充稀有状态、无结果、深分页、COUNT 与写入成本 | 为 V12 索引采用提供测量依据 |
| 正式测试表回归 | V12 后执行 45 项真实 HTTP 检查 | 验证分页、排序、身份隔离及响应契约 |

这些实验分别验证组件、SQL 和选定 HTTP 行为。完整 Service 生命周期、连接池饱和、长期负载及生产容量仍需相应实验才能得出结论。正式测试任务小表的优化器计划也保留原样，未强制使用新索引。

### 6. 日志、健康检查与恢复

- 增加请求关联编号、敏感日志处理、日志轮转及运行配置说明。
- 管理健康端口限制为本机访问，部署配置明确数据库、Redis、文件目录和迁移操作边界。
- 已有一次测试库全库逻辑备份及独立恢复演练，恢复时记录 28 张表、187873 行，包含实验夹具数据。
- 恢复后核对全表行数与摘要、列/索引/约束、Flyway 历史，并完成 47 项只读关联检查。
- 演练覆盖数据库逻辑恢复，共享 Excel 文件、Redis 会话、数据库用户授权及恢复库应用切换需分别验证。
