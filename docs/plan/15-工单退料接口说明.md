# 工单退料接口说明

更新时间：2026-10-28。对应当前源码；真实数据库迁移、CRUD、并发回滚和前端联调需要单独核验。

## 请求

`POST /api/inventory/returns`

沿用登录会话、当前企业与 CSRF 要求。请求头 `Idempotency-Key` 必填，1～64位 ASCII 字母、数字、下划线或短横线，区分大小写，当前企业内跨库存命令唯一。

```json
{
  "issueTransactionId": 100,
  "quantity": 2,
  "note": "维修后剩余备件退回"
}
```

- issueTransactionId：原领料流水ID，正整数。
- quantity：本次退回数量，大于0，最多11位整数、3位小数。
- note：可选，最多500字符。null与空字符串作为不同请求内容比较。
- 企业、操作人由可信上下文获取；仓库、备件、工单由原领料取得，不能用请求体改成其他仓库或备件。

## 规则

- 原领料必须属于当前企业，类型为 OUTBOUND、来源为 WORK_ORDER，原仓库、备件、工单及正数数量完整。
- 本实现沿用领料的当前工单负责人权限，管理员没有额外绕过。用户已确认验收后、完成后可退料，因此允许 IN_PROGRESS、AWAITING_ACCEPTANCE、COMPLETED，PENDING 不允许新增退料。
- 仓库、所属厂区、备件必须属于当前企业且可用。该启用校验为沿用现有库存写接口的实现选择；如需向停用仓库办理历史退料，需另行约定规则。
- 退回原领料所在仓库。按单次原领料关联计算累计退回量，不能超过该次原领用量；同时累计工单 returned_quantity，不能超过工单 issued_quantity。
- 退料以正数 INBOUND/WORK_ORDER 流水记录，不新增库存类型枚举，不减少原已领数量，不修改原领料流水数量或工单状态。
- 原仓库余额或工单用料行缺失时拒绝，不假设零余额、不伪造用料行；库存增加受 DECIMAL(14,3) 上限限制。
- 同一请求号、操作人、原领料ID、数量、备注和退料类型一致时，返回原流水而不重复增加库存。数值相等的2与2.000视为相同数量。已成功的普通重试可以在资源后来停用或工单状态变化后重放原结果，这不产生新的退料。

## 事务与并发顺序

1. 校验可信身份和参数，按企业及请求号普通查询成功流水。
2. 按企业及原领料ID读取来源，检查类型与关联信息。
3. 与现有库存写入保持仓库/厂区→备件→工单顺序，再锁定原领料；重新核对来源关联，避免普通快照与当前记录不一致。
4. 使用 INSERT ... SELECT 从已锁定原领料取得企业、仓库、备件和工单，SQL固定入库类型并用UUID生成流水编号；Java只提供可信身份、请求号、原领料ID、数量和备注，回填新流水主键。插入带 issue_transaction_id 的退料流水占用唯一请求号。冲突后当前读原请求流水，核对内容后重放；其他唯一键冲突不算成功。
5. 锁定当前读该原领料的全部退料数量，包含本事务刚插入的一笔，累计不能超过原领料数量。占请求号在先，使并发重复请求优先重放，不因已退满而误报超退。
6. 原子增加仓库余额和工单已退量；重查数据库流水返回真实主键与创建时间。

所有写入位于同一事务，后续异常向外抛出，交由事务整体回滚。同一原领料的请求通过原流水锁串行核对累计数量；锁冲突返回409，客户端可等待后使用原请求号及相同请求体重试。代码与XML检查不等同于真实数据库锁行为验证。

## 返回和错误

成功使用现有 `Result<InventoryTransactionVO>`：code=200，data为本次退料流水；新增 data.issueTransactionId 指向原领料。通用库存流水分页也通过Entity/VO映射暴露该字段。

400：参数或格式有误；403：不是当前负责人；404：当前企业内来源或关联资源不存在；409：类型不符、资源不可用、超退、余额/用料缺失、库存上限、请求冲突、锁冲突或关联约束失败；500：流水保存/读取失败及其他数据库异常。安全身份检查继续沿用现有状态。退料专用异常处理统一返回 Result 格式，不向客户端暴露SQL及连接信息。

## 迁移与部署前置

- 新增 V7__link_stock_return_to_issue.sql：增加可空 issue_transaction_id、企业内主键组合唯一键、来源查询索引、同企业自引用外键和退料来源类型检查。
- 旧流水保持NULL，不猜测历史退料来源，不执行自动回填。上线前须核对历史退料及旧数据归属；未关联历史记录不能据此推断为“没有发生过退料”。
- V1～V6不修改。首次开发只生成V7；2026-10-28启动故障修复时已备份、核对残留、修复失败历史并实际应用修正后的V7。本机已到V7，业务行数未变。其他环境部署前仍须核对V5/V6/V7及备份，MySQL DDL不能依赖事务回滚。
- Entity新增列会影响使用MyBatis-Plus通用Mapper的查询，因此应用新版本前必须准备好V7列，不能只在调用退料接口前才检查。
