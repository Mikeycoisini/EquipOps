# code review 提示词（每章合并前）

我要用 Superpowers 模式验收每一章，这是 code review 环节。你的任务是找问题，不是确认"看起来没问题"。

## 审查输入

1. 本章的 spec 与 plan（`docs/plan/specs/`、`docs/plan/plans/`）。
2. 本次改动的文件清单与提交记录。
3. 实现者提交的证据（命令、输出、日志、评测报告）。
4. `dev-notes/m7-chXX.md`（看有没有翻车与返工被漏报）。

## 审查维度

1. **范围**：是否只改了允许的文件？有没有顺带重构、格式化无关文件、偷偷加依赖？有没有改已执行的 Flyway 迁移？有没有出现 spec"不做"清单里的东西？
2. **越权**：是否存在从请求体取 `tenantId`/`userId` 的路径？列表/详情接口是否有跨企业反例？内部接口是否可能被浏览器直接访问？工具调用是否每次重新查库？
3. **数据与事务**：是否写了本章不该写的表？幂等键是否真唯一？条件更新是否带状态与版本？审计与业务是否同事务？
4. **AI 风险**：引用是否由服务端重取原文？资料不足是否真拒答？资料内指令是否当数据？模型给的工具名/参数是否经过程序校验？诊断结果是否带免责声明与安全提示？是否存在任何自动写入路径？
5. **编排风险**：LangGraph 的节点与边是否固定？预算硬闸是否真的拦得住第 N+1 次调用？checkpoint 是否按企业隔离、是否存了不该存的上下文？`interrupt` 恢复后是否重新校验授权？
6. **工程规范**：ServiceImpl 是否先写编号流程再逐行实现并带中文说明？响应是否统一 `Result`/`IPage`？日志是否含凭据或正文全文？新依赖是否锁版本且有批准记录？
7. **证据**：每个"已完成"是否绑定命令与输出？失败样本是否保留？是否用编译通过冒充验收、用假数据冒充联调？进程与临时数据是否收尾？

## 输出格式

```
## 结论
通过 / 不通过（不通过时列出阻断项数量）

## 阻断项（必须修）
1. 文件:行 —— 问题 —— 期望 —— 证据

## 非阻断项（记录，不阻塞合并）
1. ...

## 已验证的项
- 越权：...
- 事务：...
- 引用/免责声明：...
- 编排与预算：...

## 无法验证的项（说明缺什么证据）
- ...
```

## 判定规则

- 出现任一：跨企业数据泄露、未授权写入、伪造可验证引用、事务半成功、凭据入日志、诊断缺免责声明 → **直接不通过**。
- 缺证据的"已完成"一律按未完成计。
- 不因时间紧降低标准；也不把代码风格偏好列为阻断项。
- 发现的问题属于前面章节的，指回对应章节修，不在本章打补丁。

## 工作要求

1. 走 Superpowers 的 code review 环节；能自动触发的技能自动触发，没有就直说。
2. 审查过程记入 `dev-notes/m7-chXX.md`：关键原话、评审结论、被拒绝或纠偏的点、翻车与返工。
3. 涉及框架行为的判断（LangGraph checkpoint、事务传播、锁、序列化），先用 Context7 MCP 核对官方文档，别凭印象下结论；没有 Context7 就用官网文档并记版本。
4. 你不改代码，也不替实现者补测试、补证据。
5. 完结交付：评审结论、阻断项清单、`dev-notes` 对应段落路径。
